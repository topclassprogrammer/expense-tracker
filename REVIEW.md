# Правила Code Review

Этот файл задаёт критерии, которым должен следовать `/code-review` (и любой ручной ревью) в этом репозитории. Правила дополняют, а не заменяют `CLAUDE.md` — при конфликте `CLAUDE.md` имеет приоритет.

## Область ревью

- Ревьюить только изменения в диффе (или указанном PR/branch), не весь репозиторий.
- Ранжировать находки по серьёзности: сначала баги и уязвимости, затем упрощение/переиспользование/эффективность.
- Не поднимать стилистические придирки, покрываемые ESLint/Prettier (`npm run lint`, `npm run format`) — считать их уже решёнными тулингом.

## Общий чек-лист

### Корректность
- Граничные случаи: пустые списки, `null`/`undefined`, деление на ноль, отрицательные суммы операций.
- Гонки состояний и повторные вызовы: не приводит ли двойной клик/повторный запрос к дублированию (особенно создание операций/категорий, refresh-токен).
- Совпадают ли типы и zod-схемы между `packages/shared` и местами использования — рассинхронизация DTO бэка и форм фронта считается багом.
- Транзакционность и целостность данных при многошаговых операциях с Prisma (например, ротация refresh-токена, каскадные проверки категорий).

### Безопасность
- Утечка секретов (токены, пароли, `.env`-значения) в логах, ответах API, коммитах.
- Проверка авторизации/владения ресурсом (`assertOwned`-паттерн для категорий, `userId` в запросах транзакций) — не полагаться только на `JwtAuthGuard`.
- Валидация входных данных через zod/`nestjs-zod`, а не вручную дублируемые проверки.
- Cookie/JWT: httpOnly, правильный `path`, TTL, ротация refresh-токена не должна оставлять старые токены валидными.

### Переиспользование и упрощение
- Дублирование логики между `apps/backend` и `apps/frontend`, которое стоило вынести в `packages/shared`.
- Избыточные абстракции ради гипотетического будущего использования — отклонять, если не используется сейчас.
- Мёртвый код, неиспользуемые импорты/пропсы/эндпоинты.

### Эффективность
- N+1 запросы к Prisma там, где можно обойтись `include`/`select` или CQRS-запросом.
- Лишние ре-рендеры/перезапросы React Query (проверка `query-keys.ts`, `staleTime`, инвалидации кэша).
- Ненужные повторные вычисления сводки/агрегатов на фронте, когда данные уже приходят посчитанными с бэка.

## Специфика стека проекта

### Backend (NestJS/Prisma/CQRS)
- DTO должны идти через `nestjs-zod` из схем `@expense-tracker/shared`, а не через ручные `class-validator`/интерфейсы.
- Кросс-модульные обращения — через `@nestjs/cqrs` (Query/Command/Handler), не через прямой импорт сервиса другого модуля в обход границ.
- Публичные маршруты обязаны быть явно помечены `@Public()` — по умолчанию всё защищено `JwtAuthGuard` (`APP_GUARD`), пропуск авторизации без этого декоратора — ошибка.
- `Prisma.Decimal` в ответах API должен проходить через `DecimalSerializerInterceptor`, а не сериализоваться вручную.
- Пароли — только через `argon2`, plain-text и другие хэши недопустимы.
- Изменения `env.schema.ts` должны быть обратно совместимы или сопровождаться обновлением `.env.example`/документации — приложение не стартует без валидного `.env`.
- Refresh-токен в БД хранится только как SHA-256-хэш (`refresh_tokens.tokenHash`) — сырой токен в БД не должен попадать.

### Frontend (Next.js/React Query/Zustand)
- Формы должны валидироваться теми же zod-схемами, что и бэкенд DTO (`react-hook-form` + `@hookform/resolvers`), не собственной ad-hoc валидацией.
- Серверное состояние — через `@tanstack/react-query` с ключами из `src/lib/query-keys.ts`; ручной `useState`/`useEffect` для данных с сервера — повод для замечания.
- Access-токен живёт только в памяти (`zustand`, `auth-store.ts`) — попадание токена в `localStorage`/`sessionStorage` недопустимо.
- Обработка 401 и refresh-очередь должны идти через существующий интерсептор `api-client.ts` (`refreshPromise`), а не дублироваться в отдельных хуках.
- Новые серверные компоненты/страницы должны учитывать `middleware.ts` (редирект гостей по refresh-cookie).

### Общее для монорепо
- Общие zod-схемы/утилиты — только в `packages/shared`; прямые копипасты между `apps/backend` и `apps/frontend` — замечание уровня "упрощение".
- Изменения, ломающие сборку `packages/shared` (нужен `npm run build --workspace @expense-tracker/shared`), должны быть отмечены отдельно — они сломают `typecheck`/`db:seed` в backend и dev/build во frontend.

## Формат вывода находок

- Каждая находка: файл, строка, что не так, конкретный сценарий (вход → неверный результат/крэш).
- Не сообщать о находках без воспроизводимого сценария или явного нарушения правила выше.
- Если находок нет — явно сообщить, что ревью пройдено чисто, не выдумывать замечания ради количества.
